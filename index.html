About

The gap between promising and trustworthy

A promising model has a good metric. A trustworthy one has survived an honest attempt to break it: out-of-sample evaluation, competition against a naive baseline, permutation tests, calibration checks. My projects are built around that distinction, and it shows in the details: a stat that failed its baseline test was excluded from a scouting composite rather than quietly kept, and a headline split that rested on 16 games was reported as noise, because it was.

The same standard applies to systems. A pipeline that silently produces stale predictions is worse than one that stops and says why. The platforms in the case studies are built to refuse bad data: freshness enforcement, missing-data circuit breakers, point-in-time feature lineage, and monitoring that checks whether the model is still expressing uncertainty.

I work across the full stack because analysis that cannot be served is not finished: Python and SQL for modeling, FastAPI and PostgreSQL for serving, Next.js and TypeScript for the product surface, Docker for keeping all of it reproducible.

Engineering Philosophy

Principles the projects actually follow

Each of these is a claim you can check against the case studies, not a slogan.

Beat the baseline or sit out

Every model competes against the naive alternative out of sample. When three-point volume could not beat "stats carry over unchanged," it was excluded from the scouting composite, and when the v3 re-evaluation applied a stricter test, half of v2's top ten targets did not survive it.

Evaluation should not be able to cheat

Leave-one-out, leave-one-season-out, fold-identical CV, and era-split designs; SMOTE confined to training folds; features restricted to what was knowable before tipoff. If the evaluation can leak, the metric is fiction.

State the uncertainty

The scouting board ranks by upside probability computed from 1,000 posterior draws per player. Splits ship with permutation p-values, and the ones that fail are reported as noise. Knowing when a number is quotable is part of the analysis.

Reproducibility is a deliverable

Deterministic scripts with fixed seeds regenerate every table and chart from raw data. Feature snapshots are pinned per run. Validation lives in notebooks anyone can re-execute, and an audit script checks the largest system in seconds.

Systems should refuse to do the wrong thing

Freshness enforcement, missing-data circuit breakers, and a pre-tipoff blackout mean the prediction platform stops loudly instead of publishing quietly wrong output.

Write down the trade-offs

Design decisions are documented with what was given up: Compose-only runtime, a single production writer, duplicated feature storage. Known-limitations sections state what the models cannot see, including one inherited inconsistency kept for continuity and flagged openly.
