NBA Prediction Platform

A daily prediction product with a private ML pipeline, a read-only public API, and a web UI, engineered to run unattended. A daily prediction product is production reliability in disguise, handled with guardrails, lineage, and monitoring, because an unattended model is only as good as the pipeline feeding it.

Overview

A daily NBA prediction platform that ingests games, stats, and odds, builds point-in-time feature snapshots, generates and grades predictions from two model versions (a random forest v1 and an XGBoost v2 over the same snapshots), and serves everything through a rate-limited public API and a Next.js UI. Seven services run under one Docker Compose file. The project's substance is operational: it demonstrates what it takes for a model to run in production every day with no one watching it.

The question

Can a prediction model run itself in production, every day, without a human in the loop?

Yes, if the system is built to refuse bad data. A single scheduler owns the daily cycle, every feature snapshot is pinned to a run for point-in-time lineage, and guardrails abort the pipeline before it can predict from stale, incomplete, or failing inputs.

Why it matters

A prediction is a perishable product: worthless after tipoff and dangerous when built from stale or incomplete data. The operational challenge is the unattended daily cycle, ingestion through features through predictions through grading, which must either complete correctly or stop loudly. The user need is a reliable daily surface: today's picks, model comparison, historical performance, and strategy tools.

The data, and how it stays trustworthy

The inputs are games, box stats, and betting odds from an external API, and preparation is continuous rather than one-time, because the data changes under the system every day. Every feature-generation run snapshots its inputs under a run_id, so features are point-in-time correct by construction. Stats freshness is enforced before anything downstream runs, a 5% missing-game and a 20% feature-failure circuit breaker stop the cycle when inputs degrade, and grading re-checks the previous seven days because the league occasionally revises final scores after the fact. Historical ROI uses only pre-tipoff odds snapshots, so no reported number can borrow information that did not exist at decision time.

Method and key decisions

The architecture makes invalid states hard to reach, and each choice was made against a specific alternative. Multiple services could each write on their own schedule; instead one scheduler container owns the daily cycle, because a single update path makes partial failure detectable rather than raced around. The public API could accept writes behind auth; making it strictly read-only removes the entire class of state-corruption risk instead of managing it. Features could be stored once and updated in place; pinning every run to its own run_id spends storage on purpose, and buys an audit trail where any prediction traces to the exact snapshot that produced it and historical records survive backfills untouched. The repository documents each of these decisions together with what was deliberately given up.

Validation and reliability

Reliability here is validated operationally rather than statistically. Freshness enforcement and two circuit breakers (5% missing games, 20% feature failures) abort the cycle before degraded inputs can produce predictions; grading re-checks seven days of history because the league occasionally revises final scores; historical ROI reads only pre-tipoff odds snapshots; and monitoring alerts on staleness, coverage, and a collapse in prediction confidence. These checks establish that the served history is point-in-time correct and that failure is loud. They are claims about the system's integrity, not about model accuracy. The models themselves are deliberately standard, a random forest and an XGBoost classifier over the same feature snapshots, and their graded daily records live in the product; this page quotes none of those numbers because the platform, not the picks, is the deliverable.

Results
  • A fully automated daily workflow. Ingestion, feature snapshots, two model versions, and grading run unattended on schedule, with a status file and monitoring endpoint reporting every run.
  • Point-in-time lineage. Per-run feature snapshots create an audit trail: any prediction can be traced to the data that was actually available when it was made, and backfills cannot corrupt history.
  • Defense in depth. Stats-freshness enforcement, a 5% missing-game circuit breaker, a 20% feature-failure circuit breaker, and a 60-minute tipoff blackout keep corrupted predictions from ever being generated.
  • Monitoring that checks the model, not just the process. Alerts cover pipeline staleness and prediction coverage, and also the spread of prediction confidence, so a model that stops differentiating games is caught instead of quietly flatlining.
What the results mean

The result is a system property rather than a metric: any prediction this platform has ever served can be traced to the exact data available when it was made, and a corrupted daily run produces an alert instead of a quietly wrong slate. That is the difference between a model and a product a staff could leave running, and it is the standard the rest of this portfolio's deployed work is held to.

Limitations and scope

The limitations that matter for interpretation: the platform depends on a single external data vendor, this page describes the repository snapshot while the deployed instance has continued to evolve past it, and the operational guarantees documented here are about pipeline integrity, not about the predictive quality of any model version. The engineering trade-offs behind the design:

  • Failing loudly is the feature: the hard part of unattended operation is not the happy path but detecting the sad one. The guardrails encode specific, observed failure modes such as late-arriving box scores and API ingestion gaps.
  • Point-in-time correctness end to end: features, odds, and grading each have their own notion of "what was known when," and all three have to agree for the historical record to mean anything.
  • Freshness at the horizon: games scheduled beyond the latest stats are legitimately stale; the system distinguishes that expected case from a real pipeline failure.
Technical deep dive

Technical highlights

  • Guardrails as configuration: every threshold (freshness, missing-game rate, failure rate, tipoff grace) is an explicit, documented setting with its trade-off stated, not a constant buried in code.
  • Late score corrections are expected: grading re-checks the previous seven days because the NBA occasionally revises final scores after the fact.
  • Integrity in the analytics: historical ROI is computed only from pre-tipoff odds snapshots, so reported performance cannot benefit from information that did not exist at decision time.
  • A full product surface behind feature flags: auth, email verification, premium gating, and billing are feature-flagged and disabled by default, so the same codebase runs open or gated.

Key engineering decisions

Why Docker Compose as the only supported runtime?
Identical service versions across environments and atomic startup ordering (db, then schema-init, then the services that depend on them). The flexibility given up was flexibility the project did not want.
Why a single writer?
One scheduler owns the daily cycle, which eliminates race conditions between competing update paths and makes partial failure detectable: if ingestion fails, predictions are never generated from incomplete data.
Why a read-only public API?
External users can query but never mutate. That removes an entire class of authorization complexity and makes rate limiting and monitoring straightforward.
Why duplicate features per run?
Storage is spent on purpose. The return is an immutable audit trail (which feature version produced this prediction?) and safe historical backfills under new run IDs.

Future improvements

The stated next step is live updates as games finish rather than a single daily cycle. The auth, paywall, and billing flags already in place let the product surface expand without re-architecture.
